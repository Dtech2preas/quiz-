# D-TECH Quiz Platform System Overview
(Last Major Update: 2026 August 2rd)

## What is this platform?
D-TECH is an educational platform designed for Grade 1-12 learners in South Africa. It helps students practice past papers and CAPS/NSC curriculum questions (like Mathematics, Physical Sciences, and more) through an interactive, gamified quiz system.
Users can track their progress, earn points, buy cosmetic items, and compete on leaderboards.

## High-Level Flow
1. **Entry:** A user visits `index.html` (the landing page) or opens the Android App.
2. **Authentication:** They log in or sign up via Firebase Authentication (`login.html` / `signup.html`).
3. **Dashboard:** Once logged in, they are taken to the `dashboard.html`, which fetches their real-time stats from Firebase and displays their progress.
4. **Taking a Quiz:** The user navigates to `subjects.html` to pick a subject, and then takes a quiz in `quiz.html`. As they answer questions, the app checks if they are correct.
5. **Saving Results:** When the quiz is done, JavaScript calculates their score, XP, and D-TECH Points, and writes this back to Firebase (or IndexedDB if offline).
6. **Leaderboards & Store:** The user can view how they rank against others (`leaderboard.html`) or spend their earned D-TECH points on profile cosmetics (`store.html`).

# Updates & Changes - 2026 August 2rd
Several major architectural enhancements have been made to the platform to improve security, offline capability, scaling, and anti-cheat measures.
- **Offline-First Architecture:** The platform now fully supports offline usage via Service Workers (`sw.js`) for the browser and WebResource interception for Android. Datasets are pre-fetched and stored in IndexedDB.
- **Background Syncing:** A robust queue system (`offline_engine.js`) stores users' progress (XP, points, quiz results) when offline and aggressively syncs them back to Firebase when connectivity is restored via the Cloudflare Worker.
- **Cloudflare Worker Backend:** To handle scaling, reduce Firebase loads, and hide sensitive operations, a Cloudflare Worker (`worker.js`) now acts as the intermediary. It handles token generation, cosmetic purchases, global leaderboard caching (KV), and data aggregation.
- **Dataset Generators Engine:** Dozens of Python scripts (`generate_*.py`) dynamically generate over 1,000 distinct questions per topic, categorized into Easy, Medium, and Hard. A robust hashing mechanism ensures no duplicate questions occur.
- **Enhanced Security & Anti-Cheat:** Added `security.js` to prevent cheating by disabling text selection, copying, right-clicking, developer tools, and app switching.
- **Automated Manifests & Service Worker Caching:** Any changes to datasets update `manifest.json`, which the Service Worker and Offline Engine track to fetch exactly what changed. The Service Worker ensures a seamless offline fallback via `offline.html` when network failures happen.

# File-by-File Exhaustive Breakdown

## 1. Frontend HTML Files (The Views)

### `index.html`
**Technical Summary:** The SEO-optimized root landing page. It provides public information about the platform, features, and links to login or sign up. It does not require authentication.
**Why & Where:** To provide a marketing front for new users.

### `login.html` & `signup.html`
**Technical Summary:** Handles user authentication using Firebase Auth. `signup.html` collects metadata like grade, province, and school.
**Why & Where:** The secure entry points. All protected routes check for `localStorage.getItem('user_id')`.

### `dashboard.html`
**Technical Summary:** The main hub for authenticated users. Fetches real-time data from Firebase (or via local IndexedDB fallback if offline) to display XP, Points, and Activity.
**Why & Where:** Central navigation and progress tracking.

### `subjects.html`
**Technical Summary:** Reads the `map.json` file to generate a dynamic list of subjects and topics available for the user's specific grade.
**Why & Where:** Dynamic curriculum selection menu.

### `quiz.html`
**Technical Summary:** The core quiz engine. Loads the dataset for the chosen topic, presents questions sequentially, validates answers locally (hiding correct/incorrect feedback until the end), calculates XP/points, and writes the result to Firebase/Offline Engine. It also features `html2canvas` to generate downloadable certificates. State is auto-saved to localStorage on every question.
**Why & Where:** The main interactive test environment.

### `weekly_quiz.html`
**Technical Summary:** Specifically handles weekly exam papers by parsing `weekly_map.json`. It omits the `topic` field in submissions.
**Why & Where:** To provide structured, long-term studying via past papers.

### `leaderboard.html` & `global_leaderboard.html`
**Technical Summary:** `leaderboard.html` shows local/grade rankings. `global_leaderboard.html` fetches the Top 100 list cached in Cloudflare KV via `worker.js`.
**Why & Where:** To gamify the learning experience.

### `store.html`
**Technical Summary:** Interface for "Cosmetic Currency". Users spend D-TECH Points on avatars, borders, and themes. Purchases are transacted securely via the Cloudflare Worker.
**Why & Where:** Monetization and user reward system.

### `profile.html` & `public_profile.html`
**Technical Summary:** `profile.html` edits personal details and cosmetics. `public_profile.html` reads other users' public data via Cloudflare Worker endpoints.
**Why & Where:** Social and customization hubs.

### `earn_points.html`
**Technical Summary:** Embeds Monetag ad scripts and profitablecpmrate links. Uses native Android hooks (`window.onAdOpened`) to handle external ad links safely.
**Why & Where:** To generate revenue by rewarding users for interacting with ads.

### `stats.html`
**Technical Summary:** Displays detailed analytical data summarizing performance across subjects. Uses topic accuracy stored in Firebase.
**Why & Where:** For personalized student feedback.

### `test_run_grades.html`, `test_run_subjects.html`, `test_run_quiz.html`
**Technical Summary:** Unauthenticated trial version of the platform. Limits to 10 questions, hides explanations, uses localStorage instead of Firebase.
**Why & Where:** Try-before-you-buy feature for new visitors.

### `admin.html`
**Technical Summary:** Secured dashboard for admins. Calculates metrics client-side from the `/api/admin/data` payload. Uses HTML2Canvas for certificates.
**Why & Where:** Administrative oversight and metric tracking.

### `ecosystem.html`
**Technical Summary:** Houses external D-TECH tools (WhatsApp, University Eligibility Checker).
**Why & Where:** Keeps main app focused strictly on quizzes, pushing external tools to a separate page.

### `offline.html`
**Technical Summary:** Bundled in Android assets and cached by Service Worker to serve as a fallback when a connection failure occurs.
**Why & Where:** To prevent native Chrome error pages.

### `privacy.html`, `terms.html`
**Technical Summary:** Legal documents listing terms of service and the official contact email (`dtech2services@gmail.com`).

## 2. Core JavaScript Files (The Logic & Engine)

### `offline_engine.js`
**Technical Summary:** The heart of the offline capabilities.
- **Manifest Tracking:** Fetches `manifest.json` on startup to detect dataset changes compared to local IndexedDB.
- **Background Caching:** Downloads JSON datasets in chunks and caches them in IndexedDB.
- **Action Queuing:** If a user finishes a quiz while offline, the payload (`/api/submit-quiz`) is saved to an IndexedDB queue.
- **Syncing:** `OfflineAPI.attemptSync()` constantly tries to flush this queue to the Cloudflare Worker when connectivity restores, dispatching `offlineSyncComplete` when done.
- **Profile Merging:** `OfflineAPI.getProfile` dynamically merges pending offline XP/Points with the local cached profile so stats appear instantly updated on the dashboard before sync completes.
**Why & Where:** Ensures students in low-connectivity areas in South Africa can study seamlessly.

### `sw.js` & `register_sw.js`
**Technical Summary:** The Service Worker.
- Employs a strict offline-first strategy via `caches.match({ ignoreSearch: true })`.
- Handles exact versioning (`CACHE_PREFIX`).
- Updates are atomic: `register_sw.js` sends an `UPDATE_CACHE` message. `sw.js` downloads to a temporary cache, validates against captive portals, and promotes to live only if 100% successful.
**Why & Where:** Browser-level offline caching and progressive web app (PWA) features.

### `worker.js` (Cloudflare Worker Backend)
**Technical Summary:** The serverless backend.
- Intermediary between frontend and Firebase to protect API keys.
- **Endpoints:** Handles `/api/submit-quiz`, `/api/submit-weekly-exam`, `/api/purchase`, `/api/admin/data`.
- **KV Storage:** Manages Leaderboards (e.g., `updateLeaderboards` for dynamic subject leaderboards) and Rate Limiting.
- **Background Syncs:** Processes batched arrays of offline actions pushed by `offline_engine.js`.
**Why & Where:** Secure, scalable backend that handles business logic the client shouldn't touch (like validating store prices and updating leaderboards).

### `security.js`
**Technical Summary:** Client-side anti-cheat logic. Blocks copy/paste, right-click, developer tools shortcuts, and detects app-switching during tests. It also adds a watermark over the screen.
**Why & Where:** To maintain quiz integrity and prevent answer leaking.

### `dtech_cosmetics.js`
**Technical Summary:** Applies customized themes and fonts to the HTML DOM. Interacts closely with purchased items in `store.html`.
**Why & Where:** Renders the user's purchased cosmetic items visually on the page.

### `update_timer.js`
**Technical Summary:** Calculates when the next 5-minute data refresh interval happens on the dashboard.
**Why & Where:** Reduces server strain by only checking for live data updates periodically.

### `firebase_config.js`
**Technical Summary:** Initializes the Firebase app and Auth services.
**Why & Where:** Used everywhere an online connection to Google's backend is needed.

## 3. Dataset Generation Pipeline (Python Scripts)

### The Question Engine (`generator_base.py` & `generators_common.py`)
**Technical Summary:** The modular architecture behind question generation.
- **Separation of Concerns:** The knowledge base (facts, definitions) is strictly separated from the generation logic.
- **Schema:** Requires `a` (entity), `desc` (description), and `w` (3-5 biologically plausible distractors) in the knowledge base JSON.
- **Question Families:** Generates varied question formats based on cognitive difficulty.
- **Anti-Duplicate Hashing:** Uses MD5 hashes of the educational signature (concept + family + answer) to ensure 100% unique questions.
- **Output:** Every topic generates exactly 1000 questions (300 easy, 500 medium, 200 hard). Every question has at least 6 distractors in the `wrong_answers_pool`.
**Why & Where:** To provide an infinite, non-repetitive learning experience.

### Subject Generators (`generate_*.py`)
- `generate_math_dataset.py`, `generate_life_sciences.py`, `generate_grade12_life_sciences.py`, `generate_accounting12.py`, etc.
**Technical Summary:** Individual scripts for each subject. Subjects like Mathematics and Accounting include procedural generation for multi-step calculations to create realistic scenarios and plausible distractors based on common human errors.
**Why & Where:** Custom logic per subject to adhere to CAPS/NSC Examination Guidelines.

### Knowledge Bases (`extracted_topics.json`, `kb_*.json`)
**Technical Summary:** Raw factual data. Grade 12 Life Sciences uses modular files (e.g., `kb_meiosis.json`) while others use larger structures. Facts are often extracted from official DBE past papers and "Mind the Gap" resources.

### Utility Scripts (`build_manifest.py`, `verify_datasets.py`)
**Technical Summary:**
- `build_manifest.py`: Hashes all JSON datasets to create `manifest.json`. Called by GitHub Actions to ensure the Service Worker detects dataset updates automatically.
- `verify_datasets.py`: Validates dataset size, difficulty distributions, and cross-file duplicates before commits.

## 4. Native Android App (`android_app/`)
The Android app acts as a highly specialized WebView Wrapper targeting SDK 34 (Android 14+). It intercepts network requests to provide native integrations.

### `MainActivity.kt`
**Technical Summary:** The brain of the app.
- **WebView Setup:** Loads `https://quiz.dtech-services.co.za` and injects JavaScript interfaces.
- **AndroidDownloader:** Captures Base64 images (certificates) from the web and saves them to the native Android MediaStore.
- **AndroidCacher:** Handles background downloading of datasets.
- **AndroidExternalBrowser:** Intercepts ads and forces them to open in Chrome Custom Tabs, maintaining the app state.
- **Security:** Sets `WindowManager.LayoutParams.FLAG_SECURE` to natively block screen recording and screenshots.
**Why & Where:** Merges web flexibility with native hardware capabilities.

### `AppUpdater.kt` & `version.json`
**Technical Summary:** Implements Over-The-Air (OTA) updates. Bypasses the Play Store for direct updates. Direct GitHub release URLs are decoupled via `version.json`.
**Why & Where:** Fast, independent app updates.

### `NotificationHelper.kt`
**Technical Summary:** Uses inexact alarms (`setAndAllowWhileIdle`) instead of exact alarms to comply with Android 14+ security restrictions, preventing `SecurityException` crashes.

### `offline.html` (Android Asset)
**Technical Summary:** Android's `WebViewClient` overrides `onReceivedError` to intercept `ERROR_HOST_LOOKUP` (internet disconnected) and redirect to this native asset to prevent showing the Chrome dinosaur page.
